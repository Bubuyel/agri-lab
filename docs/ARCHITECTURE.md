# Architecture & key decisions

## 1 · System view

```
                       BUILD TIME (your laptop / Colab)                         RUN TIME (farmer's phone, offline)
 ┌──────────────────────────────────────────────────────────┐        ┌───────────────────────────────────────────────┐
 │ PlantVillage + RoCoLe ─▶ 01 vision  ─▶ crop_disease.onnx │──┐     │  React UI (7 languages, big buttons, emoji)   │
 │ WFP prices + FAOSTAT   ─▶ 02 price   ─▶ price_*.json     │  │     │    │                                          │
 │ CHIRPS rasters         ─▶ 03 rain    ─▶ rain_*.bin/json  │  ├────▶│  core/ (pure TypeScript, unit-tested)         │
 │ expert KB (en) + NLLB  ─▶ 04 advice  ─▶ advice.json      │──┘     │    vision/  price/  rain/  geo               │
 └──────────────────────────────────────────────────────────┘        │    │                                          │
        artifacts/ ──(npm run sync-data)──▶ app/public/               │  onnxruntime-web (WASM)   service worker     │
                                                                      │  = offline cache of app + models + data       │
                                                                      └───────────────────────────────────────────────┘
```

* **Models are data, not code.** The app has no server and no network calls after install. Updating a model = re-run a
  notebook, `npm run sync-data`, rebuild, re-upload.
* **`core/` has no UI imports** → it can be reused unchanged in React Native / Capacitor / a Node test.
* **Parity tests** (`app/tests/core.test.ts`) replay numbers generated by Python so the TypeScript port cannot drift from the notebooks.

## 2 · Why a PWA (and not Flutter / React Native) for *today*

You asked for the easiest framework to deploy fast with minimal bugs. Honest comparison for this MVP:

| | PWA (React) – **chosen** | Flutter | React Native (Expo) |
|---|---|---|---|
| Time to a link testers can open | **minutes** (static upload) | needs Android SDK + signed APK + distribution | needs EAS build/account; TFLite needs a custom dev client |
| On-device model | onnxruntime-web (WASM, int8) | tflite_flutter (good) | react-native-fast-tflite (native module) |
| Updates | re-upload, instant | new APK each time | OTA possible |
| Install size | ~10 MB download, no store | ~25 MB+ APK | ~30 MB+ APK |
| Verified here | **built, tested and run in a browser** | SDK not installed on this machine | not testable without a device/emulator |
| Weak point | iOS PWA limits; no background sync | bigger toolchain | native-module version friction |

The app logic is framework-independent (`core/`), and Capacitor (see DEPLOY.md §4) wraps the *same* build into an APK when
you want Play-Store distribution. Flutter becomes attractive only if you later need heavy native features.

## 3 · Model design decisions

### 3.1 Vision (notebook 01)
* **Classification, not YOLO.** Labels are per image; YOLO needs boxes and costs 3–10× more compute. Coffee polygons are used only to crop leaves.
* **Two heads** (crop · crop___condition) and **constrained decoding**: disease is chosen only among the predicted crop's classes.
* **"Not a plant"** has no labels in your data, so it is *constructed*: CIFAR-100 non-plant classes + synthetic junk frames as a `not_plant` class, with
  **15 unseen classes + synthetic frames held out** to measure rejection honestly (AUROC reported). On top, a **temperature-calibrated confidence gate** →
  "unsure, retake".
* **Closing the lab→field gap:** PlantVillage backgrounds are uniform. The *segmented* images give leaf masks → leaves are pasted on random
  backgrounds; plus exposure, white-balance, blur, motion blur, sensor noise, JPEG, low-res, grayscale (the *grayscale* folder is reproduced by augmentation).
* **Leakage control:** split by leaf group, class-stratified; fixed seeds; model selected on a *field-simulated* validation set, reported on untouched test.
* **Size:** 160 px, MobileNetV3-Small (0.96 M params in the backbone), static int8 QDQ quantisation; accuracy of int8 vs fp32 is *measured* and fp32 is
  shipped automatically if the drop exceeds 2 points.

### 3.2 Prices (notebook 02)
* Forecast target: **log price change** at horizons 1-6 months, pooled over ~1 000 national series (more data per parameter than per-series ARIMA).
* Backtest on a strict time split; compared with **naive**, **seasonal**, **ridge**, **LightGBM**. The decision rule (tree model must beat ridge by > 3 %) picks
  what ships; trees are exported as flat arrays and evaluated by 10 lines of JS (exact parity asserted).
* **Intervals** are calibrated on validation, coverage reported on test (the app shows ranges, not a single false-precision number).
* **Markets / FX offline:** nearest markets by haversine distance from GPS or chosen town; FX is *implied* by WFP `price / usdprice`, so every currency in the data converts offline.

### 3.3 Rain (notebook 03)
* CHIRPS monthly rasters (0.05°) are block-averaged to 0.5° (Africa) / 0.25° (EAC) – a phone cannot hold 5 GB and seasonal anomalies are spatially smooth.
* Output is a **tercile outlook** (below / normal / above), the same format as regional climate outlook forums, from **climatology + a small logistic model**
  on recent anomalies. Evaluated by RPSS vs equal-odds climatology on 2013-2026 (honest result: small but positive skill at 1 month, fading by 3 months), plus a
  **reliability check** and a **per-location skill flag** → low-skill places say *"low confidence: close to the usual"*.

### 3.4 Language (notebook 04) – why not an LLM on the phone
The vision model has 42 closed outputs, so the explanations are a closed set. NLLB-200 (FLORES-200) is run **once at build time**, quality-screened by
round-trip chrF, and native speakers can override sentences. This gives instant, deterministic, auditable text and **no hallucinated pesticide advice**, at
~0.2 MB instead of ~600 MB. A generative on-device model is a possible phase 2 once there is a reviewed training corpus. (An intent-classifier "Ask" chat was built and
then removed from the product; the answers screen is the diagnosis itself, in the chosen language.)

### 3.5 Open-set vision and live camera
Notebook 01 (v2) trains the 20-way crop head with extra classes **banana, bean, cassava, other_plant** ("recognised but no disease data") and a synthetic **not_plant** class
(CIFAR-100 objects/animals + noise), plus PlantDoc field photos. Result screen: *not a plant* / *not in our data yet* / *unsure* (only when the best crop probability is under
the calibrated gate) / diagnosis, always with probability bars. Held-out: not-plant AUROC 0.986, 84% of unsupported plants flagged, field-style crop/disease accuracy 72%/59%.
`LiveCamera.tsx` runs the same ONNX model (~4 ms) on camera frames and unlocks the shutter only for plant + enough light + sharp (Laplacian variance); nothing leaves the phone.

## 4 · Quality gates built in
* `npm run build` runs `tsc --noEmit` (strict) first. `npm test` = parity tests with the notebooks.
* Notebook asserts: no leaf group in both train and test; ONNX vs PyTorch numerical match; flattened-tree parity vs LightGBM; KB covers every label the model can emit.
* Every artifact reports its own measured metrics inside the JSON (`labels.json.metrics`, `price_model.json.backtest`, `rain_model.json.eval`).

## 5 · Known limits (read before showing results to farmers)
1. **PlantVillage is lab imagery.** Real-field accuracy will be lower than the test-split numbers; the augmentations help but do not replace a field validation set.
   *Action:* collect ~50 photos per crop from testers (the app never uploads photos) and fine-tune.
2. **Crop coverage = the dataset:** apple, blueberry, cherry, maize, grape, orange, peach, pepper, potato, raspberry, soybean, squash, strawberry, tomato, coffee.
   Cassava, banana, beans, sorghum, rice, millet… are **not** supported yet (they will be answered "not sure / not a plant" or confused). This is the #1 product gap for East Africa.
3. Rain skill is modest by nature (no ocean/ENSO predictors in CHIRPS). It is shown with honesty flags and should complement, not replace, national forecasts.
4. Price forecasts are statistical guesses (shown with ranges + historical error). Price data is national-median WFP survey data, not live market prices.
5. rw / rn / so / yo UI strings and NLLB translations need native-speaker review (see LOCALIZATION.md).
